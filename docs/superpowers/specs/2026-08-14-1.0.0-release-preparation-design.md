# Playtime Insights 1.0.0 发布准备设计

状态：已批准实施
设计日期：2026-08-14

## 目标

将已经合入 `main` 并由用户验收的架构重构、响应式视觉基础和侧边栏性能优化整理为
1.0.0 发布候选。统一源码、程序集、README、测试和 installer manifest 的版本元数据，
落盘可重复执行的预发布流程，并明确 GitHub Release 与 Add-on Database 的安全激活顺序。

## 发布边界

- 版本统一为 `1.0.0`，程序集版本为 `1.0.0.0`。
- AddonId 保持 `PlaytimeInsights_7094cd6b-d3a4-41d0-b7c3-f0cc535a9efd`。
- `RequiredApiVersion` 保持 `6.16.0`，除非后续依赖审计证明需要提高。
- installer manifest 在顶部增加 1.0.0 包，并保留 0.9.8 包用于历史与兼容回退。
- 当前批次生成并验证 PEXT、提交并推送源码与标签、创建 GitHub Release，并在附件可用后激活
  远端 `main`；不部署插件，也不修改用户数据。
- `manifests/addon.yaml` 暂时保留 0.9.8 截图；新版截图及 AddonDatabase 元数据 PR 是发布前独立门禁。

## 组成

1. 新建版本无关的 `docs/PRE_RELEASE_WORKFLOW.md`，记录版本冻结、自动化、客户端验收、
   确定性打包、先发布附件后激活 installer manifest、AddonDatabase 判定和回滚条件。
2. 更新版本与发布元数据：`extension.yaml`、`Properties/AssemblyInfo.cs`、README、CHANGELOG、
   `manifests/installer.yaml` 和发布元数据回归。
3. 更新架构、视觉、性能和总实施状态文档，区分工程完成、用户验收、发布准备和仍未执行的外部动作。
4. 新建 1.0.0 release notes 与客户端验收清单；更新 release checklist/readiness/roadmap/development 入口。

## 安全激活顺序

发布提交可以包含 1.0.0 installer entry，但不能在 PEXT 可匿名下载前将该提交推到远端 `main`。
推荐先把发布提交作为标签目标推送，创建 GitHub Release 并上传 PEXT；确认 PackageUrl 返回 HTTP 200
并通过 Toolbox 后，才推进 `main`。由于 AddonDatabase 已稳定指向本仓库 `main/manifests/installer.yaml`，
这一步即为自动更新激活点。

## 完成标准

- 所有当前版本断言统一为 1.0.0，历史 0.9.8 记录不被机械改写。
- installer manifest 同时包含 1.0.0 和 0.9.8，且新包 URL/日期/文件名一致。
- 架构、视觉和性能文档准确反映已完成工作与剩余发布门禁。
- 全部回归、测试项目 Release、主项目 Release 和 `git diff --check` 通过；双 clean DLL/PEXT 哈希一致。
- `v1.0.0` 与 GitHub Release 指向发布提交，附件可匿名下载且远程 manifest 通过 Toolbox 校验。
- 仅提交授权文件，`perf_test.ps1` 保持未跟踪。
