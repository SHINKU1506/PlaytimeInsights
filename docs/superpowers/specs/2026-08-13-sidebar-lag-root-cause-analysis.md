## 结论摘要

热点测试否定了本文档早期版本关于“同步读取游戏/会话并执行完整分析是当前卡顿主因”的判断。

当前数据规模为 133 个游戏、18 条会话（其中 16 条有效，涉及 4 个游戏）。在这一规模下：

- 会话仓储 `GetAll()` 中位数约 `0.0029 ms`；
- Dashboard 完整分析 `CreateSnapshotWithContext()` 中位数约 `0.3794 ms`；
- 使用等价数据刷新 Dashboard ViewModel 约 `0.65–0.75 ms`；
- 会话管理页完整刷新约 `0.23–0.26 ms`。

这些耗时不足以解释肉眼可见的侧边栏切入停顿。

目前确认的主因是：

> `SidebarItem.Opened` 每次都构造一个新的 `PlaytimeInsightsDashboardView`。新视图包含较长、未虚拟化的
> WPF 视觉树，首次进入布局系统时需要同步完成样式/模板解析、测量、排列和布局更新；这一过程发生在
> UI 线程，并处于页面可显示之前。ViewModel 虽被缓存，但 View 及其视觉树没有复用。

本机独立进程 WPF 基准中，新 Dashboard View 的首次 `Measure + Arrange + UpdateLayout` 约为
`157–160 ms`，离屏渲染另约 `22–23 ms`。同一个已布局 View 再次执行布局仅约 `0.0034 ms`。
这个数量级和“切入时明显卡顿”一致，且新建/复用之间的差异直接锁定了触发条件。

此外确认一个次要热点：会话管理页封面转换器在 UI 线程同步读取并解码图片，18 张真实本地封面一次
转换的中位数在不同运行中约为 `175–263 ms`。实际页面当前有 16 行、4 个不同游戏，重复图片仍可能
因 `IgnoreImageCache` 被重复解码。它主要解释会话管理页的额外卡顿，不是 Dashboard 的首要原因。

同步数据分析仍是大数据量下的可扩展性风险，但不是当前数据规模下的主因。

## 验证范围与方法

测试均基于当前 `main` 源码与真实本地数据规模；输出只记录数量、大小和耗时，不输出游戏名、会话内容
或文件名。为减少宿主、JIT 和缓存相互干扰，WPF 布局场景在独立进程中运行，预热后重复 7 次取中位数。

测试覆盖：

1. 真实数据仓储读取、完整分析和两个 ViewModel 刷新；
2. 当前 main Dashboard 完整视图的构造、绑定、首次布局、离屏渲染和复用布局；
3. 折叠主要动态区域后的 Dashboard 对照组；
4. 本地已部署旧版 `0.9.8` Dashboard 对照组；
5. 真实封面文件的存在性检查与 WPF 图片解码；
6. 1 千、1 万和 10 万会话的合成数据扩展性测试；
7. 反编译/源码核对，用于区分路径拼接、文件 I/O、时区解析和 WPF 对象创建。

本测试的 WPF 离屏渲染是 CPU 侧代理，不等同于 Playnite 中硬件合成后的端到端帧时间。因此结论依据
不是某一个绝对数值，而是新建 View、折叠内容、旧版 View 和复用 View 之间稳定且可重复的差异。

## 热点测试结果

### 1. 当前真实数据的读取与分析不是主因

真实数据规模：

| 项目 | 数量/大小 |
| --- | ---: |
| Playnite 游戏 | 133 |
| 会话总数 | 18 |
| 有效会话 | 16 |
| 涉及游戏 | 4 |
| `sessions.json` | 13,775 bytes |
| `games.db` | 716,800 bytes |

匿名基准结果：

| 操作 | 中位数 | P95/补充 |
| --- | ---: | ---: |
| `SessionRepository.GetAll()` | 0.0029 ms | 0.0082 ms |
| `CreateSnapshotWithContext()` | 0.3794 ms | 0.6927 ms |
| 全部会话按本地日切分 | 0.0057 ms | — |
| 全部会话按本地小时切分 | 0.0089 ms | — |
| Dashboard 等价完整刷新 | 0.65–0.75 ms | — |
| 会话管理页等价完整刷新 | 0.23–0.26 ms | — |

因此，早期版本将 `Games.ToList()`、会话克隆排序和完整分析列为当前最高热点，没有运行时证据支持。
它们确实都在 UI 线程同步执行，但“同步”本身不能证明它们已经构成可感知卡顿。

### 2. 新建 Dashboard 视觉树的首次布局是主因

预加载数据、预热 JIT、移除 `Loaded` 数据刷新影响后的独立进程结果如下，单位为毫秒：

| 场景 | 构造 | 首次 Measure | Arrange | UpdateLayout | 离屏 Render | 同 View 再布局 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 当前 main，完整视图 | 7.16 | 52.12 | 6.71 | 100.25 | 22.50 | ≈0.00 |
| 当前 main，主要动态区全部折叠 | 7.42 | 52.54 | 7.04 | 97.88 | 22.58 | ≈0.00 |
| 本地旧部署版 `0.9.8` | 6.53 | 49.92 | 6.57 | 99.84 | 22.83 | ≈0.00 |

主要动态区包括星期分布、小时分布、高级统计标签/单元格、热力图、周期活动、排行、异常项和会话明细。
全部折叠后耗时没有实质改善，旧部署版与当前 main 也接近。这说明：

- 不是某一张图表、热力图或响应式面板单独造成卡顿；
- 当前响应式布局改动不是回归源；
- 成本来自整个长页面视觉树首次参与 WPF 样式、模板和布局流程；
- 对同一个已布局 View 再布局约 `0.0034 ms`，证明“每次重新创建 View”是决定性触发条件。

对应源码行为是 `PlaytimeInsights.cs` 的 Dashboard `SidebarItem.Opened` 每次返回新的
`PlaytimeInsightsDashboardView`；Dashboard ViewModel 被插件实例缓存，但 View 没有缓存。会话管理页也
采用每次新建 View 的方式，因此同类成本会在那里重复出现。

### 3. 封面同步解码是会话管理页的次因

`CoverImageConverter` 的转换路径包含：

- `File.Exists`；
- `BitmapImage.BeginInit/EndInit`；
- `CacheOption = OnLoad`；
- `CreateOptions = IgnoreImageCache`；
- `DecodePixelWidth = 96`。

18 张真实本地封面合计约 3,952,905 bytes，宽 411–1066 px、高 560–1507 px。测试结果：

| 操作 | 结果 |
| --- | ---: |
| 18 次 `File.Exists` | 中位数约 1.343 ms |
| 18 次完整 `CoverImageConverter` | 不同运行的中位数约 175–263 ms，P95 最高约 314 ms |

`PlayniteApi.Database.GetFullFilePath()` 的实现实质是路径组合，不是此前文档所称的同步 I/O 热点；真正
的成本是图片打开、解码和 WPF 图像对象初始化。`IgnoreImageCache` 还会削弱相同封面的复用效果。

### 4. 同步完整分析是扩展性风险，而非当前主因

合成数据展示了会话增长后的风险：

| 合成规模 | Dashboard 完整快照中位数 |
| --- | ---: |
| 1,000 会话 / 20 游戏 | 约 8 ms |
| 10,000 会话 / 200 游戏 | 约 54 ms |
| 100,000 会话 / 2,000 游戏 | 约 558 ms |

在跨 DST 的 10,000 会话场景中，完整分析约 472 ms，其中逐小时切分约 418 ms，占约 89%。已有
100,000 会话回归场景约 755 ms。会话管理页合成刷新在 10,000、50,000、100,000 会话时约为
51、257、534 ms。

因此异步化、取消和算法优化仍有价值，但应作为大数据量治理阶段，不能替代当前视觉树主因的修复。

## 对早期诊断的修正

早期版本中的以下表述需要明确撤回或收窄：

1. **“`Games.ToList()` 是单步最高成本”**：当前规模下未被热点测试支持。
2. **“Daily 每次都创建自定义时区”**：不准确。有效 `TimeZoneId` 走
   `TimeZoneInfo.FindSystemTimeZoneById`；只有 ID 缺失或无效时才创建自定义时区。Daily 仍缺少缓存，
   但当前数据下不是热点。
3. **“会话管理页也执行 AnalyticsService”**：不准确；该页没有 Dashboard 完整分析链。
4. **“可观察集合全量发布”**：不准确。首屏发布受分页限制，最多 200 行；不过筛选、`CreateItems` 和
   `ApplyCoverImages` 仍会处理全部匹配项。
5. **“`GetFullFilePath` 是同步 I/O”**：不准确；封面文件存在性检查与图像解码才是 I/O/CPU 热点。
6. **“直接用 `Task.Run` 包住读取和分析即可”**：风险过高。`Database.Games` 的跨线程安全没有保证，
   分析结果还包含未冻结的 WPF `PointCollection`，并依赖本地化资源。不能把整个现有调用链原样搬到
   线程池。

## 实施结果（2026-08-14）

P0 与 P1 已在 `main` 实施：

- `PlaytimeInsights` 在同一插件进程中只创建一个 Dashboard ViewModel 和一个
  `PlaytimeInsightsDashboardView`；`Opened` 返回缓存 View，`Closed` 只清除 `activeDashboard`；
- `Loaded` 保持唯一自动刷新事件入口，每次事件最多执行一次 DataReload。Loaded 不被当作导航次数，
  WPF 因主题或模板重建产生的额外 Loaded 仍按同一规则刷新；
- 缓存完整视觉树后，滚动偏移、焦点等纯 View 状态允许随 View 保留，不做关闭时重置；
- 新增共享 `CoverImageCache`，按规范化路径和解码宽度缓存冻结缩略图，以文件长度和
  `LastWriteTimeUtc` 失效，并以 access-order LRU 限制为 512 条目；
- 首次/文件变化后的封面解码仍同步执行。后台 STA 解码、Dashboard 分析异步化和会话页 View 复用不在
  本批次范围。

TDD 增加 7 项回归：3 项验证 View、视觉树和刷新边界复用，4 项验证路径规范化、跨 Converter 共享、
文件失效、宽度分离、LRU 淘汰、冻结图像和 `OnLoad` 文件句柄释放。RED 阶段恰好这 7 项失败且旧测试
全通过；整合后显式重建测试项目，107/107 全部通过。Release 与测试项目构建均为 0 警告、0 错误；
10 万会话分析为 623 ms，schema 4 的 10 万会话载入为 1,141 ms，未突破既有发布预算。

当前整合 Release 的独立热点基准进一步得到：

| 场景 | 轮数 | 中位数 |
| --- | ---: | ---: |
| 新插件实例 + 新 Dashboard View 首次布局总计 | 8 | 65.8777 ms |
| 同一 View 经 Closed/Open 后复用布局总计 | 20 | 0.0003 ms |
| 100,646-byte 临时 PNG，fresh cache 首次解码 | 12 | 3.1271 ms |
| 同路径 warm cache 命中 | 30 | 0.0863 ms |

基准同时确认：连续 Opened、Closed 后重开及 DashboardScrollViewer 均保持引用相同；缓存命中返回同一
冻结对象；两个 Converter 共享对象；`OnLoad` 后源文件可删除，冻结图像仍可用。该基准是独立进程的
CPU/WPF 布局与解码代理，不等于 Playnite 硬件合成后的端到端屏幕首帧；宿主重挂载、主题切换和实际
交互体感仍由部署验收确认。

### 已实现：P0 Dashboard View 复用

Dashboard View 与 ViewModel 一样保留到插件进程结束。自动化测试证明连续 Opened 及 Closed 后重开
返回同一 View、同一 DataContext 和同一 DashboardScrollViewer。真实 Playnite 宿主中的重挂载 Loaded、
滚动位置和主题行为仍需在部署验收中确认。

### 已实现：P1 同步封面缓存

- 已按规范化路径与解码宽度缓存缩略图；
- 不同 XAML Converter 实例共享同一个 512 条目缓存；
- 保留 `IgnoreImageCache`，由应用层文件戳负责一致性和失效；
- 缓存值已冻结；未来如需后台解码，仍必须增加解码后文件戳复核和过期结果抑制。

### P2：治理大数据量分析链

先在 UI 线程捕获最小、不可变的纯 CLR DTO，再在后台执行不依赖 WPF/Playnite 数据库对象的计算，最后
回到 UI 线程创建并发布 WPF 对象。配合 generation、`CancellationTokenSource` 和结果过期检查。

算法侧优先优化跨 DST 的逐小时边界扫描，并避免在筛选条件未变化时重跑完整分析。

### P3：加入生产环境分段测量

在正式改动前后记录：`Opened`、View 构造、`Loaded`、数据刷新各阶段，以及下一次
`CompositionTarget.Rendering` 的时间。这样可在 Playnite 宿主中得到真正的端到端首帧数据，并验证
离屏基准得出的主因。

## 验收标准

- 相同数据和窗口尺寸下，第二次及后续 Dashboard 切入不再创建完整新 View；
- 生产分段计时确认后续切入不再承担首次视觉树布局成本；
- 会话管理页相同封面不重复同步解码；
- 快速连续切换页面不会显示过期结果，也不会泄漏事件订阅；
- 现有回归测试继续通过，主题、DPI、语言切换和游戏停止后的刷新行为正常。

## 最终判断

审查方向“侧边栏进入仍有 UI 线程同步工作”是合理的，但早期文档把相关性当成了主因，严重度排序不
合理。经过真实数据热点测试和独立 WPF 对照实验，目前可以确认：

1. **当前主因：每次导航新建完整 Dashboard View，重复支付长视觉树的首次 WPF 布局成本；**
2. **次因：会话管理页同步、无有效复用地解码封面；**
3. **未来风险：会话达到万级后，同步时区切分和完整分析才会成为主导热点。**

P0/P1 已完成自动化验证；后续重点是 Playnite 宿主验收，以及在数据量增长后建设安全的 DTO 异步分析
管线。
